# Incident Report: HTTP Request Flood Against Production Web Application

**Incident date:** 14 June 2024 | **Prepared by:** Security Analyst | **Source evidence:** `logs.txt` (5,033 lines) | **Classification:** Application-layer denial of service (HTTP flood) / automated abuse

## 1. Introduction

On 14 June 2024 a critical alert was raised on a production web server running an nginx + uWSGI stack under supervisord. Analysis of the server log snapshot shows that a single external host sent **5,000 automated POST requests to the root endpoint (`/`) in roughly 132 seconds**, at peaks of about 188 requests per second. The traffic was generated by a scripted client (`python-requests/2.31.0`). The flood produced one server-side error (HTTP 500) and consumed worker capacity that legitimate users depend on.

The purpose of this report is to document what happened, explain how it was identified, propose a mitigation strategy, justify it against industry standards, and describe implementation and ongoing monitoring. It also records additional weaknesses found during the investigation that are unrelated to the flood itself but increase risk.

## 2. Detailed Attack Analysis

### 2.1 Summary of findings

| Item | Finding |
| --- | --- |
| Attacking IP | `54.145.34.34` |
| Targeted endpoint | `/` (HTTP `POST`) |
| Request volume | 5,000 requests from the attacker (99.8% of all HTTP traffic) |
| Tool / client | `python-requests/2.31.0` (Python script) |
| Duration | 17:26:35 to 17:28:47 UTC, about 132 seconds |
| Peak rate | About 188 requests per second |
| Response codes (all traffic) | 5,010 × `200`, 1 × `500` |
| Referer header | None (`-`), unlike real browser traffic |

These values were extracted with the four analysis scripts supplied (`0-attack_ip.sh`, `1-endpoint.sh`, `2-count_attack.sh`, `3-library.sh`) and verified independently against the raw log.

### 2.2 Source

The log contains 5,011 HTTP request lines from only two client IPs. `54.145.34.34` accounts for 5,000 of them. The other address, `51.158.115.139`, made 11 requests using a normal Chrome 125 browser user agent, supplying a Referer of `http://75.101.231.9:4001/` and spacing requests minutes apart. This is consistent with a human user and is treated as legitimate. The origin of `54.145.34.34` appears to be a cloud-hosted address (an AWS-style range). Ownership should be confirmed through WHOIS and an abuse report, but attribution to a specific actor cannot be established from these logs alone.

### 2.3 Targeted endpoint and request pattern

Every attacker request was `POST / HTTP/1.1` and every successful response was exactly 1,941 bytes. Identical response sizes mean the application returned the same page each time, so the requests were repeated submissions of the same form rather than varied probing. The server processed each one fully, which is why the abuse was expensive: a POST typically triggers application logic (and possibly database access), unlike a cheap static GET.

### 2.4 Timeline of events (UTC)

| Time | Event |
| --- | --- |
| 17:25:02 to 17:25:04 | Container starts; supervisord launches `nginx`, `uwsgi` and `quit_on_failure`. Migrations run via `alembic upgrade head`. |
| 17:25:12 | First legitimate request (`GET /`) from `51.158.115.139`. |
| 17:26:04 | Legitimate user submits a form (`POST /`). |
| 17:26:35 to 17:26:49 | **Burst 1:** about 2,700 POSTs in 15 seconds from `54.145.34.34`. |
| 17:27:25 to 17:27:30 | **Burst 2:** about 711 POSTs in 6 seconds. |
| 17:28:07 to 17:28:20 | **Burst 3 (ramp):** about 337 requests, including the only `500` error at 17:28:20. |
| 17:28:40 to 17:28:47 | **Burst 4:** about 1,252 POSTs in 8 seconds. |
| 17:28:55 | Last log entry; a legitimate user request still succeeds. |

The on/off burst pattern shows a script run repeatedly or in loops with pauses, rather than a sustained distributed attack.

### 2.5 Impact

- **Availability:** about 5,000 requests competed with real users for a limited number of uWSGI workers and nginx connections. One request failed with HTTP 500 during the flood, a sign the application was under strain.
- **Resource consumption:** CPU, worker processes, and possibly database connections were consumed by repeated form submissions.
- **Data integrity (possible):** if the POST handler stores or emails submitted data, up to 5,000 junk records or messages may now exist and should be checked and purged.
- **Confidentiality:** the logs show no evidence of data theft, injection payloads, authentication bypass, or code execution. No sign of compromise beyond abuse of availability was found.

### 2.6 Root cause

The server has **no rate limiting**. Nothing limits how many requests one client may send per second, so a single inexpensive script could monopolize the application. This is the "thing that limits the usage of the server" that was missing: a request rate limit (throttling) per client.

### 2.7 Additional weaknesses identified

| # | Weakness | Evidence in log | Risk |
| --- | --- | --- | --- |
| 1 | No rate limiting or connection limiting | 188 req/s accepted from one IP | Denial of service, resource exhaustion |
| 2 | No automation defense on the form (no CAPTCHA, anti-CSRF token, or bot detection) | Referer-less POSTs from `python-requests` accepted with `200` | Spam, form abuse, scripted submissions |
| 3 | Supervisor runs as root | `CRIT Supervisor is running as root` | A compromised process has full privileges |
| 4 | Supervisor `unix_http_server` has no authentication | `CRIT Server 'unix_http_server' running without any HTTP authentication` | Local process control without credentials |
| 5 | Insufficient logging | `X-Forwarded-For` field shows `-`; no request time or upstream latency | Poor attribution behind proxies; hard to measure impact |
| 6 | No automated alerting | Flood lasted over two minutes before analysis | Slow detection and response |
| 7 | Fixed `sleep 10` in startup script | `prestart.sh` | Fragile start-up; minor availability risk |
| 8 | No WAF or reputation filtering in front of the app | Known-scripted user agent not challenged | No first line of defense |

## 3. Proposed Mitigation Strategy

A layered approach that stops this attack now and reduces future exposure:

1. **Per-IP rate limiting at nginx** (primary control), returning HTTP 429 when the limit is exceeded.
2. **Connection limiting** per IP to stop one host holding many workers.
3. **Tighter limits on `POST` requests** than on `GET`, since POSTs are costlier.
4. **Automated-traffic defenses on the form:** CSRF token, CAPTCHA or proof-of-work challenge, and optional blocking or challenging of non-browser user agents.
5. **Temporary block** of `54.145.34.34` at the firewall or security group while limits are rolled out.
6. **Edge protection:** place a CDN/WAF (for example Cloudflare, AWS WAF) in front of the server for volumetric and distributed cases.
7. **Hardening:** run supervisord as a non-root user, protect or disable its control socket, and improve logging.

## 4. Justification for the Proposed Solution

- **It addresses the root cause.** The incident happened because a single client faced no limit. Rate limiting removes that condition directly, with little cost to legitimate users, whose observed behaviour was one request every few minutes.
- **It matches industry guidance.** Rate limiting and throttling are recommended in the OWASP API Security Top 10 (unrestricted resource consumption), the OWASP Application DoS guidance, and CIS and NIST (SP 800-61 on containment, SP 800-53 SC-5 on denial-of-service protection) control families.
- **It is cheap and fast.** nginx's built-in `limit_req` and `limit_conn` modules need no new software, can be deployed in minutes, and are low risk.
- **It is layered.** Rate limiting alone cannot stop a distributed attack from many IPs, so the WAF/CDN and bot defenses complement it (defense in depth).
- **Alternatives considered:** manual IP blocking alone is reactive and trivially bypassed by changing address; scaling up servers only raises the cost of the attack and does not stop it; a WAF alone costs more and takes longer to tune. The combination chosen gives the best protection for effort.

## 5. Steps for Implementation

**Phase 1: Containment (immediate, under 1 hour)**

1. Block `54.145.34.34` at the cloud security group or host firewall (`iptables`/`ufw`).
2. Preserve evidence: copy `logs.txt` and nginx/uWSGI logs to read-only storage with a checksum.
3. Check the application database or mail queue for junk records created via `POST /`.

**Phase 2: Eradication (same day)**

4. Add rate limits to the nginx `http` and `server` blocks, for example:

```nginx
limit_req_zone  $binary_remote_addr zone=perip:10m rate=5r/s;
limit_req_zone  $binary_remote_addr zone=post_perip:10m rate=1r/s;
limit_conn_zone $binary_remote_addr zone=connperip:10m;

server {
    limit_req_status  429;
    limit_conn_status 429;
    limit_conn connperip 20;

    location / {
        limit_req zone=perip burst=10 nodelay;
        if ($request_method = POST) { set $limit_post 1; }
        # apply the stricter POST zone (e.g. in a dedicated location or via map)
        limit_req zone=post_perip burst=5 nodelay;
        # ... existing uwsgi_pass configuration ...
    }
}
```

5. Validate with `nginx -t`, reload with `nginx -s reload`, then test with a short load test from a staging host to confirm that excess requests receive `429`.
6. Add a CSRF token and CAPTCHA to the form, and log `$http_x_forwarded_for`, `$request_time` and `$upstream_response_time` in the nginx `log_format`.
7. Optionally install **fail2ban** with a filter that bans IPs generating repeated `429` responses.

**Phase 3: Recovery and hardening (within one week)**

8. Purge any junk data created during the attack and confirm normal service and response times.
9. Run supervisord as an unprivileged user and restrict or password-protect `unix_http_server`.
10. Put a CDN/WAF in front of the application with managed bot and rate rules.
11. Replace the fixed `sleep 10` with a proper database readiness check.
12. Document the runbook and test it in a tabletop exercise.

## 6. Post-Implementation Monitoring

| Area | Tool / method | What to watch |
| --- | --- | --- |
| Request rate | nginx access logs shipped to ELK/Loki/Splunk; Grafana dashboards | Requests per second per IP; sudden POST spikes |
| Rate-limit effectiveness | Count of `429` responses | A sudden rise signals an attack or limits set too low |
| Server health | Prometheus + node exporter, uWSGI stats | CPU, memory, busy workers, request queue length |
| Errors | Alerts on 5xx ratio | Any rise in `500`/`502`/`503` |
| Automated banning | fail2ban or WAF logs | Banned IPs and repeat offenders |
| Alerting | Alertmanager, PagerDuty or Slack | Threshold example: more than 100 requests/10 s from one IP, or 5xx above 1% |
| Threat intelligence | AbuseIPDB, WAF reputation lists | Reputation of repeat source IPs |
| Review | Weekly log review, monthly limit tuning, post-incident review | Adjust thresholds based on real traffic |

Baselines should be recorded first: normal traffic here is a handful of requests per minute, so thresholds can be set tightly.

## 7. Conclusion

The incident was an application-layer HTTP flood: 5,000 scripted `POST /` requests from `54.145.34.34` using `python-requests/2.31.0` within about two minutes. It caused strain and one server error, but the logs show no evidence of data theft or system compromise. The underlying weakness was the absence of any request rate limit, compounded by missing bot defenses, root-privileged supervisor processes, and limited logging and alerting.

Implementing per-IP rate and connection limits, form protection, edge filtering, and proactive monitoring will stop this class of attack, and the hardening steps reduce wider risk. A post-incident review should follow, with the runbook and thresholds updated based on lessons learned, so the organization can detect and contain similar events faster in the future.

*Note: source attribution is limited to what the logs show; the attacker's identity and intent have not been established. Figures were computed from the provided log snapshot and cover only that period.*
